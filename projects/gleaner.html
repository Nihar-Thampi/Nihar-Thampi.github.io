Gleaner

A web-scraping platform that tracks every change in the data and tells you when one matters.

What it’s for

Teams that watch other websites, for competitor prices, stock levels, listings or public data, don’t just need the data once. They need to know what changed since yesterday, and to hear about it when a change matters.

Most scrapers dump a fresh file on every run and leave the comparing to someone else. Gleaner keeps every item’s history, records field-level changes between runs, checks each run’s data quality, and fires alerts on rules you set, such as “price drops 15% or more”.

It’s also built to scrape responsibly: approved sites only, robots.txt always obeyed, polite rate limits and an honest crawler identity. Admins approve domains and manage the team, API keys and webhooks. Editors build and run scrapers. Viewers read and export.

How a run works

  1. A domain is approved

    Before anything is fetched, an admin approves the domain, records why scraping it is acceptable, and sets a rate limit. Every scraper on that site shares the limit.

  2. A scraper is built

    CSS selectors define the items, fields, pagination and detail pages, with a live preview against the real page. Or describe the fields in plain English and let the local model propose the selectors.

  3. Pages are fetched politely

    Static pages come through httpx, and JavaScript-heavy ones through headless Chromium with Playwright. robots.txt is read first and its Crawl-delay applied. Failed requests retry with exponential backoff and honour Retry-After, and every redirect hop is checked against policy again.

  4. Fields are extracted and cleaned

    Each field has a type: text, number, price, URL, yes/no or list. Prices handle currencies and thousands separators, and optional regexes and value maps tidy the rest.

  5. Items are compared with the last run

    Items are matched across runs by key fields, and each one is recorded as new, changed, removed or returning, with field-level diffs and a value history. A scraper’s first run only sets the baseline.

  6. The run is checked

    Quality checks look at fill rate per field, rejected rows, broken selectors, drops in item count, implausible jumps and mass removals. Alerts fire, and the local model writes a plain-English summary of what changed.

  7. The data goes where it’s needed

    CSV, Excel and JSON exports, a read API with API keys, and HMAC-signed webhooks when a run finishes or an alert fires.

What it does

Scraping

  • Selector builder with live preview
  • Static HTML or a headless browser for JavaScript sites
  • Schedules from hourly to weekly, with live progress, a run log and cancellation
  • Retries, backoff and size limits

Change tracking

  • New, changed, removed and returning items, with field-level diffs
  • Value history charts, such as price over time
  • Removals recorded only on complete runs, so one failed page can’t make items look deleted
  • Alerts on field changes, new items, removals, failed runs and quality flags

AI, with an offline fallback

  • A selector assistant that tests its own suggestions on the live page and gets one correction round
  • AI repair for broken scrapers, keeping the same field names
  • Plain-English run summaries that flag anything that looks wrong
  • A log of every prompt, response, model, latency and token count

Compliance

  • Domains are pending, approved or blocked
  • robots.txt to RFC 9309: a missing file allows everything, one that can’t be reached blocks everything
  • A User-Agent that names GleanerBot with a contact email, and a page telling site owners how to opt out
  • Private, loopback and link-local addresses refused for crawling, robots.txt and webhooks

The demo data

The seed script creates a workspace with three users and six scrapers, so every feature has something real to show.

The centrepiece is Ridgeline Outfitters, a fictional practice store served by the backend itself. Its prices and stock change every day based on the date, and 30 days of history are built by replaying each past day through the real extractor and ingest code. That history includes a pricing glitch for the quality checks to catch.

The other scrapers run once for real against public sandboxes made for scraping practice: Books to Scrape for pagination and ratings mapped to numbers, Quotes to Scrape for lists, its JavaScript edition as a failing scraper that AI repair fixes by switching to browser rendering, and two pages from Scrape This Site for a 250-row table and paginated stats with composite keys.

Decisions and trade-offs

Politeness is in the core, not a setting

Domain approval, robots.txt, shared rate limits and address checks sit in the fetch path every request goes through, so no scraper can skip them. When robots.txt can’t be read, the safe answer is to wait.

AI suggestions come with a test

A proposed selector is only useful if it extracts something. The assistant’s output is run by the real extractor against the live page, and gets one chance to correct fields that come back empty.

A local model is enough when its work is checked

Selector suggestions, repairs and summaries run on Qwen2.5 through Ollama, with no cost per call. Because every suggested selector is tested on the real page, a smaller local model is safe to use: when it gets a field wrong, the fill rate shows it instead of bad data slipping into a scraper. The context window is set large enough for a whole simplified page of HTML.

Don’t cry wolf

A first run is a baseline rather than 142 “new item” alerts, and removals only count on complete runs. Feeds and alerts stay worth reading.

Demo history through real code

The practice store’s 30 days of history go through the same extractor and ingest path as live runs, so the demo exercises the real system rather than seeded rows.
